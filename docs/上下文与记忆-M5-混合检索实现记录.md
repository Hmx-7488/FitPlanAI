# 上下文与记忆 M5：长期记忆混合检索实现记录

> 日期：2026-08-12
> 状态：M5.0 已完成，并通过独立审查与全量门禁

## 1. 目标

M4 已解决“什么事实可以成为长期记忆”。M5.0 继续解决“在大量长期记忆中，怎样稳定、可解释地找到当前真正需要的事实”。本阶段固定采用关键词与向量的混合检索，不把是否使用 hybrid 延后到 M6。

## 2. 核心架构

```text
用户消息
  -> SQLite 权威过滤（confirmed、未删除、有效期、user_id）
  -> keyword 排名 ----------------------┐
  -> 独立 Chroma memory collection -----+-> RRF -> 安全/业务重排
                                        |
                                        -> Context Builder -> 实际使用追踪

记忆确认/编辑/删除
  -> SQLite 状态 + index_revision + outbox（同一事务）
  -> 后台 worker 幂等 upsert/delete
  -> 失败退避重试；主链路不被 embedding/Chroma 阻塞
```

### 为什么 SQLite 是唯一真值

向量 metadata 只用于候选定位和版本校验，不能决定记忆是否有效。每个向量命中必须按 `memory_id` 回查 SQLite，并同时验证 `content_fingerprint` 与 `index_revision`。因此删除、过期、替代和编辑后的旧 embedding 即使暂时残留，也不会进入模型上下文。

### 为什么使用独立物理目录

现有知识库重建会整体替换 `backend/data/vectorstore`。记忆 collection 若与知识库共用目录，会在知识重建时被删除。因此长期记忆使用 `backend/data/memory_vectorstore`，模型/索引版本通过独立 collection 隔离，禁止不同维度或模型版本混用。

## 3. 检索模式

- `keyword`：确定性中文 bigram/BM25 与现有业务 cue，完全不初始化 embedding。
- `vector`：支持同义表达；所有结果经过 SQLite 生命周期和版本终检。
- `hybrid`：两路排名使用 RRF `Σ 1 / (k + rank)` 融合，不比较量纲不一致的原始分数。
- `hybrid` 或 `vector` 遇到索引缺失、embedding/Chroma 故障时，显式降级为 keyword，并记录 requested/effective mode 和原因。
- 健康敏感记忆只有 confirmed 才能建索引；召回时安全优先但总数有界。

## 4. 索引一致性

- `user_memories.index_revision`：内容或索引资格改变时单调递增。
- `user_memory_index_outbox`：只保存 ID、operation、revision 和错误类型，不复制记忆正文。
- 状态变更和 outbox 同事务：不会出现“SQLite 已保存、索引事件丢失”。
- worker 处理前重新读取 SQLite；旧 revision 自动标记 obsolete。
- Chroma 文档 ID 固定，重复 upsert 幂等。
- 编辑立即以 SQLite 新正文参与 keyword；旧向量因 revision/fingerprint 不一致立即失效。
- 删除立即被 SQL 阻断，后台完成向量清理。
- 支持全量 rebuild 和 orphan cleanup；单用户 rebuild 不做全局 orphan 删除，避免跨用户误删。

## 5. 可观测性与隐私

新增 retrieval run/hit 两级记录：

- requested/effective mode、降级原因；
- keyword/vector 候选数与 stale 过滤数；
- 通道、通道 rank、RRF/final rank；
- `included_in_context`：只表示事实真正序列化进模型请求，不声称模型一定采纳；
- query 只保存 SHA-256，不保存原文；
- outbox 错误只保存异常类型，不保存敏感正文。

聊天以 Context Builder 最终保留的 memory IDs 标记 used；计划以实际写入 `confirmed_memories` 的 IDs 标记 used。telemetry 写失败会降级，不影响聊天或计划生成。

## 6. 测试策略

使用临时 SQLite、fake vector backend 和确定性结果，不依赖真实 DashScope、`.env` 或本地 Chroma 数据。重点覆盖：三模式、RRF、跨用户隔离、candidate/deleted/expired/superseded 排除、旧版本拒绝、故障降级、outbox 重试/幂等、编辑失效、重建和孤儿清理。

## 7. 面试表达

> 将长期记忆从“SQL 中按规则排序”升级为可治理的 Hybrid Retrieval：以 SQLite 作为生命周期真值，关键词与向量两路召回后使用 RRF 融合，并通过 fingerprint/revision 终检解决异步向量索引的陈旧读问题；利用事务 outbox、幂等 upsert、退避重试和可重建索引保证最终一致性，同时追踪每条记忆的检索通道、排名和是否真正进入模型上下文。

这个亮点的价值不在“接了一个向量库”，而在于同时回答了召回质量、敏感数据治理、异步一致性、故障降级、可解释性和可评测性。

## 8. M6 方向

M6 不再决定“要不要混合检索”，而是基于固定评测集比较 keyword/vector/hybrid 的 Recall@K、MRR、硬约束漏召回率、降级率、延迟与 embedding 成本，并据此调整 RRF、候选窗口和模型版本。
