# 上下文与记忆 M4：跨会话长期记忆

## 1. 本阶段结论

M4 已完成一条可运行的跨会话记忆闭环：

```text
用户原话
  -> 响应结束后的候选提取
  -> 严格结构校验 + 服务端敏感等级复核
  -> 普通记忆自动确认 / 健康敏感记忆进入候选态
  -> 去重、冲突替代、时效和来源记录
  -> 按当前问题召回已确认记忆
  -> 注入聊天 Context Builder 和后续计划生成
  -> 用户查看、确认、忽略、修改或遗忘
```

长期记忆没有替代正式档案和会话摘要：正式档案仍是权威健康事实，会话摘要仍只服务单次会话连续性，长期记忆只保存跨会话有价值且经过治理的用户信息。

## 2. 数据模型与状态

[UserMemory](../backend/app/models/user.py) 保存：

- 类型与稳定 `memory_key`；
- 结构化内容和可读事实；
- 来源会话、来源消息和内容指纹；
- `candidate / confirmed / rejected` 确认状态；
- `normal / health_sensitive` 敏感等级；
- 生效、过期、替代和软删除信息；
- 创建主体、置信度和更新时间。

[UserMemoryAudit](../backend/app/models/user.py) 记录创建、确认、拒绝、修改、替代和删除事件。审计快照只保存生命周期状态，不复制完整健康内容，降低日志和审计表的敏感数据扩散。

新表由现有 `create_all` 初始化链路创建。旧版 `user_memories` 表通过可重复执行的增量迁移补充 `active_slot`，回填每个用户、每个 key 的唯一生效值，并建立数据库唯一索引；不删除存量表和数据。

## 3. 候选提取与安全边界

[user_memory_service.py](../backend/app/services/user_memory_service.py) 只把用户消息交给候选提取器，不从助手回复中生成用户事实。

模型输出必须通过严格 Pydantic schema：

- 只允许 preference、goal、habit、constraint、experience；
- `memory_key` 必须是稳定的小写点分键；
- 每轮最多 5 条；
- 置信度和文本长度有边界；
- 无合法 JSON 时整轮放弃，不写入半结构化内容。

伤病、过敏、疾病、药物、医生限制和进食障碍不只依赖模型分类。服务端会再次扫描 key、文本和结构化内容；只要命中健康敏感语义，就强制进入 `health_sensitive + candidate`，确认前不能召回。普通记忆也只有在置信度达到配置阈值后才会自动确认，低置信度内容保留为候选。

候选内容和用户编辑内容还会经过指令特征过滤；长期记忆在 Prompt 中以 JSON 数据注入，并由位于上下文末尾的系统规则再次声明“不可执行”，降低把历史文本误当系统指令的风险。

提取、摘要和聊天主链路彼此故障隔离。记忆模型或数据库失败时只记录 ID、任务名和错误类型，聊天回答仍然完成，不记录用户完整原话。

## 4. 去重、冲突与遗忘

- 相同用户、相同 key、相同内容指纹不会重复写入；并发冲突由数据库约束兜底，单条冲突不会回滚同批已成功的候选。确认或编辑竞争同一 active slot 时服务层会回滚，API 返回可处理的 `409 Conflict`，不暴露数据库异常或返回 500。
- 普通记忆自动确认；同 key 出现新的已确认值时，新记录通过 `supersedes_memory_id` 指向旧记录，旧记录设置 `valid_until`。
- `active_slot` 唯一索引保证同一用户、同一 key 最多只有一个当前生效的已确认值。
- 健康敏感候选只有在用户确认时才执行替代。
- 候选、拒绝、过期、被替代和软删除记录不会进入召回。
- 删除 API 使用软删除并写审计；后续可在 M5/M6 增加物理清除与来源会话级联重建策略。

## 5. 相关性召回与上下文优先级

第一版采用确定性混合打分，不引入额外向量基础设施：

- 中文双字和英文词重合；
- 记忆类型线索；
- diet、training、goal、sleep 领域线索；
- 已确认健康约束安全加权。

零相关普通记忆不会注入。中文单字匹配已明确禁用，避免“不错”和“不喜欢”仅因共享“不”字产生误召回。

Context Builder 中的优先级为：

```text
本轮输入与系统安全规则
  > 权威用户档案
  > 当前有效计划
  > 相关且已确认的长期记忆
  > 会话摘要和近期消息
  > RAG / Tool Artifact
```

每轮消息诊断保存实际使用的 `memory_ids` 和数量，便于追溯回答使用了哪些记忆。长期记忆内容仍被标为不可信数据，不能把其中的文本当成系统指令。

## 6. 聊天、计划与用户控制

- 聊天请求在生成前召回相关记忆，并通过 [context_builder.py](../backend/app/services/context_builder.py) 注入。
- 计划生成通过 [plan_service.py](../backend/app/services/plan_service.py) 读取已确认记忆，以低于正式档案的优先级传给 Agent。
- [chat.py](../backend/app/api/chat.py) 提供列表、确认、拒绝、修改和删除 API，并验证 `user_id` 所有权。
- [ChatView.vue](../frontend/src/views/ChatView.vue) 增加记忆抽屉：健康候选与已确认记忆分组显示，支持确认、忽略和遗忘。

当前应用仍是本地单用户产品，没有真正的登录鉴权。非 `development` 环境下，全部 `/api/chat` 入口会在未配置服务端访问密钥时拒绝启动访问，并要求反向代理注入 `X-Memory-Access-Key`；这能阻止接口裸奔，但仍只是部署边界的共享密钥，`user_id` 所有权校验也不能替代生产身份认证。多用户远程部署前仍需增加用户级认证和细粒度授权。

## 7. 固定离线评测

入口：

```powershell
cd backend
python -m app.evals.long_term_memory
```

固定 4 个场景覆盖：

- 饮食问题只召回饮食偏好；
- 训练问题优先召回已确认健康限制；
- 无关问题不召回普通记忆；
- 过期、删除和拒绝记录不参与召回。

本次固定集结果为 4/4，通过率、precision 和 recall 均为 100%。这是确定性构造样例结果，只说明这些治理分支被覆盖，不能当作真实用户流量或真实模型抽取准确率。

## 8. 本阶段边界与 M5

尚未完成：

- 真实模型抽取 precision/recall 与延迟成本量化；
- 记忆编辑表单、来源消息跳转、审计时间线；
- 按记忆类别关闭自动保存；
- 物理删除、会话删除后的摘要和记忆级联失效；
- ~~向量/混合检索工程化~~ 已在 M5.0 完成；大规模效果、延迟和成本对比进入 M6；
- 多用户身份认证、会话绑定和细粒度授权；当前共享访问密钥只用于部署边界防护。

M5.0 已完成可解释混合召回和使用追踪底座；M5.1 将围绕完整“记忆中心”继续开发，而不是扩充隐藏的自动记忆：用户应能理解 Agent 为什么记住、在哪里使用、如何纠正，以及删除后会影响哪些上下文。

## 9. 面试表达

> 我把长期记忆设计成一个受治理的数据系统，而不是把历史聊天直接做向量检索。Agent 只从用户原话提取严格结构化候选；普通偏好可以自动确认，伤病、过敏、疾病和用药由服务端二次识别并强制要求用户确认。记忆带来源、指纹、时效、替代关系和审计，只有已确认且未过期的相关记忆才能进入 Context Builder 和计划 Agent；每轮还记录实际使用的 memory ID，支持用户确认、纠正和遗忘。
