# ADR-001：分层上下文与长期记忆

## 1. 决策状态

状态：**Accepted（已接受，M0-M4 已实施）**

本 ADR 决定 SlimAgent 将聊天上下文、会话摘要、跨会话长期记忆和权威健康档案拆分为不同层级，并通过统一的 Context Builder 在 token 预算内组装。目前 M0-M4 已完成：上下文预算、会话摘要、覆盖游标、Artifact Microcompact、受治理的跨会话长期记忆及最小用户控制入口均已落地；M5/M6 继续建设完整记忆中心与真实模型量化。

## 2. 背景

M0 基线阶段的聊天链路已经具备：

- 会话和消息数据库持久化。
- SSE 流式输出与消息状态记录。
- 用户档案、最新计划、页面上下文和 RAG 资料注入。
- LangGraph 风险识别与知识检索。

M0 基线阶段的上下文加载规则位于 [chat_service.py](../backend/app/services/chat_service.py)：用户新消息先写入数据库，然后查询该会话按 ID 倒序的最近 10 条消息。构建模型消息时跳过刚写入的新消息，最后再显式追加当前消息。因此当时模型实际获得的是：

```text
系统提示 + 用户档案 + 最新计划 + 页面上下文 + RAG
+ 最多 9 条历史消息
+ 当前用户消息
```

这个旧方案简单且可预测，但存在以下限制；当前实现已由 M1-M4 针对这些限制完成第一轮治理：

1. 长对话早期的重要目标、约束和未完成事项会被固定窗口截断。
2. 不同消息的 token 差异很大，固定条数无法控制真实上下文大小。
3. 旧会话中的稳定偏好不能参与新会话。
4. 大型 RAG 或工具结果可能挤占比用户消息更重要的上下文。
5. 健康敏感信息如果只存在于旧聊天、尚未进入正式档案，可能被遗忘。

M0 离线基线的 6 个场景中只有 3 个关键事实进入当前上下文，可用率为 50%；两个安全事实场景只有 1 个可见。详见 [[上下文与记忆-M0基线报告]]。

## 3. 决策目标

- 完整原始消息可以追溯，不以摘要代替原始记录。
- 长对话不会因固定消息截断而稳定遗忘早期关键状态。
- 跨会话只使用经过治理的长期记忆，不直接检索全部旧聊天作为事实。
- 权威健康档案始终高于摘要和模型推断。
- 上下文组装拥有明确的 token 预算、优先级和可观测数据。
- 摘要或记忆组件失败时，聊天主链路能够安全降级。
- 用户最终能够查看、确认、纠正和删除长期记忆。
- 设计可以通过离线评测和生产指标量化，而不是依赖主观体验。

## 4. M0-M2 第一轮不在范围

以下是 M0-M2 当时明确排除的范围，其中长期记忆与最小控制入口已在 M4 补齐：

- 不在 M0-M2 实现长期记忆 UI；M4 已提供最小查看、确认、拒绝和遗忘入口，完整记忆中心仍属于 M5。
- 不把所有内部服务改造成 MCP。
- 不引入新的向量数据库或外部记忆 SaaS。
- 不自动把模型提取的健康敏感信息写入正式档案。
- 不删除或破坏现有聊天记录。
- 不把摘要生成放在用户流式响应的关键路径上。

## 5. 核心决策

### 5.1 分为四种数据，而不是一个大摘要

| 数据层 | 用途 | 作用域 | 权威级别 |
| --- | --- | --- | --- |
| 原始消息 `chat_messages` | 审计、回看、重新摘要 | 单会话、永久或按用户删除 | 事实来源，不直接等于权威事实 |
| 会话摘要 `conversation_summaries` | 维持当前会话目标、结论和待办 | 单会话 | 中 |
| 长期记忆 `user_memories` | 跨会话稳定偏好、目标、习惯 | 用户级 | 中高，取决于确认状态 |
| 权威档案 `users` 及业务表 | 伤病、过敏、身体数据、当前有效计划 | 用户级 | 最高 |

优先级：

```text
本轮用户明确输入
> 权威档案和当前有效计划
> 已确认且未过期的长期记忆
> 会话摘要
> 近期原始消息
> 未确认推断
```

### 5.2 使用覆盖游标进行增量会话摘要

`conversation_summaries` 的计划字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 摘要版本 ID |
| `conversation_id` | 所属会话 |
| `summary_json` | 结构化摘要 |
| `summary_text` | 可读降级文本 |
| `covered_through_message_id` | 本摘要覆盖的最后一条原始消息 |
| `source_message_count` | 覆盖消息数量，便于诊断 |
| `estimated_tokens` | 摘要估算 token |
| `model` | 摘要模型 |
| `status` | pending/completed/failed/superseded |
| `created_at` / `updated_at` | 审计时间 |

更新摘要时只读取：

```text
message.id > covered_through_message_id
AND message.id <= 本次任务启动时捕获的 target_message_id
```

`target_message_id` 在任务开始时固定，避免摘要执行过程中新增消息导致边界漂移。只有摘要成功持久化后才推进覆盖游标。

### 5.3 压缩后保留近期原始消息尾部

会话上下文由以下部分组合：

```text
最新有效会话摘要
+ covered_through_message_id 之后的未摘要消息
+ 满足最小近期预算的原始消息尾部
```

近期尾部必须：

- 不拆分用户消息与紧随其后的助手响应。
- 未来引入工具消息后，不拆分 `tool_use` 与 `tool_result`。
- 优先保留当前回合、最近纠正和最新约束。
- 按 token 而不是固定消息条数选择。

具体 token 数不在 ADR 中写死，由 M1 根据当前模型窗口和基线数据配置。

### 5.4 工具和 RAG 结果优先 Microcompact

当上下文超预算时，裁剪顺序为：

1. 去除重复和低相关 RAG 文档。
2. 将旧工具结果替换为带来源引用的结构化摘要。
3. 压缩旧会话消息为会话摘要。
4. 保留用户当前请求、健康硬约束、当前计划和近期原始消息。

不得为了保留长工具输出而移除过敏、伤病、医生限制或当前用户明确要求。

### 5.5 长期记忆必须经过治理

长期记忆计划字段：

| 字段 | 说明 |
| --- | --- |
| `user_id` | 记忆所属用户 |
| `memory_type` | preference/goal/habit/constraint/experience |
| `memory_key` | 用于同类冲突和替代 |
| `content_json` / `content_text` | 结构化内容和可读文本 |
| `source_conversation_id` / `source_message_id` | 来源追踪 |
| `confirmation_status` | candidate/confirmed/rejected |
| `sensitivity` | normal/health_sensitive |
| `valid_from` / `valid_until` | 时效 |
| `supersedes_memory_id` | 显式替代旧记忆 |
| `created_by` | user/model/system |
| `deleted_at` | 可遗忘的软删除标记 |

保存策略已经确认：

- 普通偏好可以自动保存，但必须向用户提示并允许撤销。
- 伤病、过敏、疾病、药物、进食障碍等健康敏感信息必须经用户确认。
- 敏感候选记忆在确认前不能用于修改正式档案或生成硬约束计划。
- 被拒绝、删除、替代或过期的记忆不得进入上下文。

### 5.6 原始消息保留与删除

当前个人项目默认保留完整原始聊天用于追溯，归档不等于删除。长期记忆阶段必须提供：

- 真正删除某个会话。
- 删除某条长期记忆。
- 删除来源消息后使相关摘要/记忆失效或重建。
- 记录删除影响，避免摘要继续泄露已经删除的内容。

## 6. Context Builder 责任

新建统一 Context Builder，聊天服务不再自行拼接所有上下文。其输入包括：

- 模型上下文窗口和输出预留。
- 当前用户请求。
- 安全规则、用户档案、最新计划和页面上下文。
- 已确认长期记忆。
- 会话摘要和近期消息。
- RAG 结果与工具结果。

输出包括：

- 发给模型的消息列表。
- 各组成部分的估算 token。
- 被保留、压缩和丢弃的项目 ID。
- 使用的摘要版本和覆盖游标。
- 使用的长期记忆 ID。
- 降级原因和预算告警。

日志不得记录完整敏感内容，只记录 ID、类型、数量、token 和状态。

## 7. 摘要结构

会话摘要使用固定结构化 schema，至少包含：

- `current_goal`：本会话当前目标。
- `confirmed_facts`：用户明确确认、但不提升为正式档案的事实。
- `constraints`：本会话约束，并标注是否已进入正式档案。
- `decisions`：已经达成的决定。
- `open_questions`：仍需用户回答的问题。
- `pending_actions`：未完成事项。
- `corrections`：用户对旧信息的纠正。
- `source_range`：起止消息 ID。

摘要 Prompt 必须：

- 将消息内容视作被总结的数据，防止其中的提示注入控制摘要器。
- 不总结系统提示、内部配置和密钥。
- 不把模型推断升级成用户确认事实。
- 保留数字、单位、否定词、时间范围和冲突关系。
- 输出严格 JSON，并通过 Pydantic 和后端语义校验。

## 8. 触发策略

第一版采用确定性触发，不把是否压缩交给聊天 Agent：

- Context Builder 预测本轮动态上下文超过配置阈值时触发摘要任务。
- 从上次覆盖游标之后增长达到配置阈值时可提前异步更新。
- 摘要任务串行化：同一会话同一时间只允许一个任务推进游标。
- 聊天请求不等待后台摘要；超预算时可同步使用安全裁剪并在下一轮使用新摘要。

阈值由配置提供，并在 M1 根据模型窗口确定，避免照抄 Claude Code 的绝对 token 数。

## 9. 并发与幂等

- 摘要任务使用 `(conversation_id, covered_through_message_id, target_message_id)` 作为逻辑幂等键。
- 写入时比较当前有效摘要的覆盖游标；旧任务不得覆盖覆盖范围更大的新摘要。
- 失败任务记录错误类型和重试次数，不记录敏感原文。
- 连续失败达到阈值后熔断，聊天回退到安全裁剪。
- 长期记忆写入通过 `memory_key`、来源消息和内容指纹去重。

## 10. 失败与降级策略

| 故障 | 降级行为 |
| --- | --- |
| token 估算失败 | 使用保守字符估算和更大输出预留 |
| 摘要模型失败 | 使用旧摘要 + 近期消息；没有旧摘要则安全截断 |
| 摘要 JSON 无法解析 | 不推进游标，记录失败并回退 |
| 记忆召回失败 | 不使用长期记忆，不影响基本聊天 |
| 冲突无法判断 | 使用本轮输入/正式档案，并提示用户确认 |
| 删除后重建失败 | 相关摘要和记忆先标记不可用，避免继续注入 |

## 11. 评测策略

### 11.1 M0 确定性上下文可用性评测

入口：

```powershell
cd backend
python -m app.evals.context_memory
```

评测只判断回答所需事实是否进入动态上下文，不调用 LLM，因此可在 CI 中稳定执行。测试集覆盖：

- 近期偏好。
- 长对话早期目标。
- 正式档案中的过敏信息。
- 仅存在于早期聊天的敏感伤病。
- 跨会话稳定偏好。
- 近期目标纠正。

### 11.2 M1-M6 后续指标

- Context availability：所需事实是否进入上下文。
- Summary fidelity：摘要是否保持数字、否定、约束、待办和纠正。
- Memory precision/recall：召回记忆是否相关且正确。
- Conflict resolution accuracy：新旧目标、偏好和档案冲突是否正确处理。
- Safety constraint adherence：健康硬约束是否全部遵守。
- Token、延迟和成本：改造前后对比。
- Fallback availability：摘要/记忆失败时主链路是否仍可用。

模型回答质量评测与上下文可用性评测分开，防止把“模型碰巧答对”误认为上下文系统正确。

## 13. 备选方案与否决原因

### 固定最近 N 条消息

实现最简单，但无法处理消息 token 差异，也会稳定遗忘早期信息。只保留为降级路径。

### 每轮都总结整个会话

成本和延迟高，容易产生摘要漂移；改用覆盖游标和增量摘要。

### 把全部旧聊天放入向量库直接检索

相似度无法表达权威级别、时效、确认、删除和替代关系；旧聊天可以作为候选来源，但不能直接成为长期事实。

### 只依赖 LangGraph Checkpointer

Checkpointer 解决图状态持久化，不自动解决 token 预算、摘要正确性、跨会话记忆治理和用户隐私。

### 第一阶段引入外部 Memory SaaS

会增加隐私、供应商锁定和调试复杂度，同时掩盖本项目要展示的核心工程能力，因此暂不采用。

## 14. 影响

正面影响：

- 长对话连续性和跨会话个性化具备可解释架构。
- token、延迟和质量可以被量化。
- 形成 AI 应用 / AI Agent 面试中的差异化项目亮点。
- 健康敏感信息拥有比普通聊天摘要更严格的治理。

代价：

- 增加摘要版本、并发、删除重建和评测复杂度。
- 需要额外模型调用和后台任务机制。
- 必须持续维护记忆 schema、冲突规则和安全测试集。
