# 聊天 Agent M6A：Tool Calling 实现记录

> 日期：2026-08-13
> 状态：核心实现、专项测试、真实模型固定评测与浏览器验收已完成；全量提交门禁以对应提交记录为准

## 1. 阶段目标

M1-M5 解决了“有限上下文里保存什么、压缩什么、怎样召回长期记忆”。M6A 继续解决“本轮问题究竟需要读取哪些业务数据”。聊天不再为每类问题固定查询全部数据，而是由 qwen 原生 Tool Calling 在受控目录中选择最少的只读工具，再由 LangGraph 负责有界执行、降级和结果汇总。

这一阶段仍坚持只读边界：Agent 可以解释档案、计划、打卡、餐食、食物、动作、知识和长期记忆，但不能直接修改用户数据。写操作进入后续“生成草案 → 展示差异 → 用户确认 → CAS 写入”的单独阶段。

## 2. 核心链路

```text
用户消息 + 当前页面
  -> 风险规则前置判断
  -> qwen bind_tools(tool_choice=auto)
  -> LangGraph plan_tools
  -> 工具名/参数去重 + 调用预算
  -> LangGraph execute_tools
       ├─ 服务端绑定 user_id
       ├─ Pydantic 严格参数校验
       ├─ SQLAlchemy 有界只读查询
       ├─ Hybrid RAG / Memory Retrieval
       └─ 单工具超时与安全错误
  -> Tool Artifact Microcompact
  -> Context Builder 统一 token 预算
  -> qwen 流式生成
  -> meta/tool/delta/citations/done SSE
  -> 持久化安全工具轨迹与实际上下文使用状态
```

工具路由和执行使用单个 LangGraph 编排器。最终回答仍复用已有流式生成器，避免在 M6A 同时重写稳定的消息持久化、取消和摘要后台链路。

## 3. 第一批只读工具

| 工具 | 数据来源 | 典型问题 |
| --- | --- | --- |
| `get_user_profile` | SQLite 用户档案 | 我的忌口、伤病和训练条件是什么 |
| `get_latest_plan` | SQLite 最新计划 | 当前热量、宏量、餐单或训练安排是什么 |
| `get_recent_checkins` | SQLite 打卡 | 最近体重和执行情况怎样 |
| `get_meal_summary` | SQLite 分餐记录 | 今天总热量和蛋白质是多少 |
| `search_foods` | 结构化食物库 | 鸡胸肉每 100g 的营养 |
| `search_exercises` | 结构化动作库 | 指定部位、器械和难度的动作候选 |
| `search_knowledge` | 专业知识 Hybrid RAG | 需要证据的训练、营养和风险问题 |
| `search_memories` | 长期记忆 Hybrid Retrieval | 用户过去确认过的稳定偏好与目标 |

## 4. 权限与安全设计

### 身份不进入模型参数

`user_id`、`conversation_id` 和来源消息 ID 由服务端放入请求级 `ChatReadToolContext`。模型看到的工具 schema 中不存在 `user_id`、SQL 或任意查询表达式，因此即使提示注入要求读取其他用户，也无法改变服务端查询范围。

### 有界执行

- 单轮最多调用 4 个工具，配置上限不超过 8 个。
- 同名同参调用先去重。
- 模型返回的调用 ID 不作为内部主键；服务端重新生成单轮唯一 ID，避免重复 ID 串联引用或覆盖前端台账。
- 单工具默认 15 秒超时，失败只返回稳定错误码，不返回堆栈和内部异常。
- Tool Agent 使用独立于聊天消息生命周期的 `AsyncSession`；数据库工具超时、异常或客户端取消时只回滚工具会话，避免失败事务和 ORM 过期状态污染聊天历史、回答生成与消息状态提交。
- 单工具内容默认最多 6000 字符，超出后保存有界预览，再交给 Artifact Microcompact 和总 token 预算二次裁剪。
- `page_context` 最多 10000 字符、6 层嵌套、500 个节点；浏览器不能借页面上下文无限扩张模型输入。
- 工具参数使用 `extra="forbid"`，列表、日期、分类、数量和文本长度均有显式边界。
- 来源链接前后端都只允许绝对 `http/https`，历史脏数据中的 `javascript:` 不会成为可点击链接。

### 不暴露推理过程

前端展示的是“调用了什么、是否成功、结果是否实际进入回答、来源是什么”，而不是 chain-of-thought。工具内容不直接作为可执行 HTML 渲染，LLM 和检索资料都按不可信数据进入最终 Context Guard。

## 5. 降级与可观测性

- 工具路由模型失败：显式标记 `PLANNER_ERROR`，回退到 M5 已有的风险判断与固定 RAG 主链路。
- 单个工具失败或超时：该工具标记为“已跳过”，其他工具和最终回答继续执行。
- Knowledge/Memory 的底层向量能力故障：沿用各自 hybrid retriever 的关键词降级，不把索引故障扩大为聊天故障。
- 只有 Context Builder 实际保留的 Tool Artifact 才会标记 `included_in_answer`，引用和记忆 usage 也按相同引用 ID 终检，避免把“查过”误报成“回答用过”。
- `context_json` 保存工具名、状态、耗时、来源 ID、降级原因和上下文预算，不保存 planner 的内部推理文本。

## 6. 前端交互

SSE 新增 `tool` 事件，事件顺序为：

```text
meta -> tool... -> delta... -> citations -> done
```

聊天消息下方增加轻量“Agent 数据查询”台账：

- 展示工具业务名称和安全摘要；
- 区分“已用于回答 / 已查询 / 已跳过”；
- 来源列表默认折叠；
- 失败不展示内部异常；
- 桌面和 390px 移动端均无横向溢出。

## 7. 评测与验证

固定路由集包含 10 个场景：闲聊、当前计划、近期打卡、当日餐食、食物营养、动作与专业依据、长期偏好、计划执行对比、档案约束和提示注入。

2026-08-13 使用当前配置的真实 qwen planner 运行：

- Exact Match：10/10；
- Precision / Recall：100% / 100%；
- 越权工具调用：0；
- 提示注入用例：未调用不存在的写工具。

这些数字只代表小规模固定离线集，不代表生产流量准确率。评测器复用生产 tool schema 和有界选择函数；CI 使用确定性 planner 验证指标计算和安全回归，真实模型评测可通过以下命令复跑：

```bash
cd backend
python -m app.evals.chat_tool_selection
```

本次 `qwen-plus` 运行的逐场景选择结果保存在 `backend/tests/fixtures/chat_tool_selection_qwen_baseline.json`，用于审计本页的单次基线声明；模型或提示词更新后必须重新运行并新建带日期的基线，不能覆盖历史结果伪装成连续指标。

浏览器验收使用 mock SSE，覆盖桌面和移动端工具轨迹、来源展开、危险协议禁用、控制台错误和横向溢出，不读取本地用户数据。

## 8. 面试表达

### 30 秒版本

> 我把聊天从“每轮固定塞入全部业务数据”升级成受控 Tool-Calling Agent：qwen 只负责在 8 个只读领域工具中选择最少调用，LangGraph 负责调用预算、去重、超时、降级和轨迹；身份由服务端请求上下文绑定，不暴露给模型，工具结果经过 Microcompact 和统一 token 预算后才进入回答。前端只展示安全工具台账和实际来源，不暴露思维链，并用固定真实模型路由集验证工具选择与越权调用。

### 高频追问

#### 为什么不让模型传 user_id？

模型参数属于不可信输入。身份必须来自认证/服务端上下文；否则提示注入或模型幻觉可能构造其他用户 ID。M6A 的每个 SQL 查询都闭包绑定当前用户，工具 schema 无法改变这一点。

#### 为什么工具轨迹不等于思维链？

产品需要的是可审计的外部动作，而不是模型的隐式推理文本。台账只记录工具名、稳定状态、耗时、来源和是否进入上下文，既能解释答案依据，也不会泄露系统提示或不可靠的内部推理。

#### 为什么工具执行后还要走 Context Builder？

Tool Calling 解决“取什么”，Context Builder 解决“有限窗口里保留什么”。工具可能返回长餐单、动作步骤或多篇知识，仍需要与档案、近期聊天、摘要和长期记忆共享一个确定性的 token 预算。
